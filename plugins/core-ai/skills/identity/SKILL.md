# core-ai — Repository Instrumentation Engine

core-ai analyzes a repository and generates tailored `.claude/` configurations — rules, commands, and hooks — that encode the repo's conventions, workflows, and enforcement needs into machine-readable, enforceable context.

Think of it as **instrumentation** in the observability sense: adding probes and metadata so AI agents understand how to work in the repo, without changing the repo's actual code or behavior.

## Why This Exists

Every repository has implicit conventions that determine "how we work here." Today, these are transferred to AI agents via ad-hoc instructions, repeated prompting, and trial-and-error. Instrumentation makes them explicit, discoverable, and enforceable.

The gap: every major AI coding tool (Claude Code, Cursor, Copilot, Windsurf) has converged on needing a machine-readable project description. None of them **generate** it from repository analysis. They all require manual authoring. core-ai fills this gap.

## Philosophy

### Transparent, Not Magic

Always show what was detected and what will be generated. Never silently write files. Every generated file includes a provenance header tracing back to the detection signals and user input that produced it.

### Additive, Not Invasive

Like OpenTelemetry instrumentation, core-ai adds observability without changing business logic. Rules, commands, and hooks live alongside code, not inside it. Existing user-authored `.claude/` files are treated as ground truth — never overwritten or modified.

### Progressive, Not Overwhelming

Start with essentials (build, test, style) from auto-detection. Advanced sections (security, release, architecture) are opt-in. The user can accept sensible defaults or customize deeply.

### Convention-Driven

Generated outputs follow standardized patterns. Rule files have consistent structure. Commands use correct frontmatter. Hooks follow the Claude Code schema. This consistency makes the output predictable and maintainable.

## Non-Negotiables

1. **Never overwrite user files.** If a `.claude/rules/` file exists and was not generated by core-ai (no provenance header, or not tracked in the manifest), treat it as sacred. Augment around it, never replace it.

2. **Always show what will be generated.** Before writing any file, present the full list of files and a summary of each. The user must confirm before generation proceeds.

3. **Create a manifest for idempotency.** Every instrumentation run creates or updates `.claude/.instrumentation.json`. This enables re-instrumentation without duplication, drift detection, and auditability.

4. **Never modify source code.** core-ai's output domain is `.claude/` only. It reads source code, configs, and git history for analysis but never writes outside `.claude/`.

5. **Respect enforcement preferences.** Hooks (automated enforcement) are only generated when the user explicitly opts in. Rules (guidance) are the default. The user controls the strictness spectrum.

## The Instrumentation Maturity Spectrum

| Level | Name | Description |
|-------|------|-------------|
| 0 | **AI-Unaware** | No agent configuration. Agent guesses everything from code. |
| 1 | **AI-Ready** | Has instruction file(s) with build commands, style, structure. |
| 2 | **AI-Enabled** | Has scoped rules, boundaries, testing conventions, workflow defs. |
| 3 | **AI-First** | Designed with AI collaboration as first-class concern. Specs drive development. Hooks enforce conventions. The repo teaches any agent how to work in it. |

core-ai moves a repository from level 0 toward level 3, one instrumentation pass at a time.

## Relationship to Other Plugins

- **core-kit** provides routing intelligence (intent → skill). core-ai provides configuration generation (repo → `.claude/`).
- **core-spec** provides spec-driven development (plan → implement). core-ai provides the foundation that makes spec-driven development effective (the repo already has rules and conventions encoded).
- **system-maker** creates claude-kit plugins. core-ai creates project-level `.claude/` configuration. Different output domains, complementary goals.
